Context for whoever (human or LLM) picks this up next. v1.2.4 shipped on
2026-08-04 evening. Owner reported two bugs the next morning; both were

## 1. "Check for Updates" never detected 1.2.4 — FIXED, verified live

**Symptom:** Settings → Check for Updates said "Al Quran is up to date" even
though 1.2.4 had shipped. No Home banner either.

**Root causes (two, stacked):**

1. `.github/workflows/flutter-release.yml`'s "Publish app update config" step
   was gated on `steps.play.outputs.enabled == 'true' && ...` — i.e. tied to
   whether the Play Store upload happened, not just whether the Cloudflare
   publish secrets were present. Fixed: now gated only on
   `steps.app_update_publish.outputs.enabled`.
2. **Bigger issue, found after the first fix:** even when published, the R2
   object was going nowhere reachable. `alquranreader.com` (bare root) is
   already the custom domain for the `al-quran-web` Cloudflare Pages project.
   The `al-quran-editions` R2 bucket only had a custom domain on
   `editions.alquranreader.com` — never on the root. The already-shipped app
   hardcodes `https://alquranreader.com/app-update.json`
   (`lib/core/app_update_config.dart:16`), so nothing could serve that path.
   This wasn't a regression — the soft-update feature had **never** actually
   published anywhere; `gh secret list` showed `CLOUDFLARE_API_TOKEN`,
   `CLOUDFLARE_ACCOUNT_ID`, `APP_UPDATE_R2_BUCKET` had never been set on the
   repo, and no R2 bucket had ever held an `app-update.json` object.

**Fix:** deployed a new Cloudflare Worker at `infra/app-update-worker/`,
routed to exactly `alquranreader.com/app-update.json` (path-scoped, so it
doesn't fight the Pages catch-all for the rest of the site). It reads object
`app-update.json` from the `al-quran-editions` R2 bucket. Deployed via
`cd infra/app-update-worker && npx wrangler deploy` — already live.

Also added a **verification step** to the release workflow: after publish, it
re-fetches the live URL and fails the release (`::error::` + exit 1) if the
deployed `latestVersion` doesn't match what was just shipped. This is the
guard that would have caught this whole class of failure earlier.

**Manually published today's config** to unblock existing 1.2.4 installs:
```bash
dart run tool/generate_app_update_config.dart --latest-version="1.2.4" \
  --minimum-supported-version="1.0.0" --remind-after-days="7" --output=/tmp/app-update.json
npx wrangler r2 object put "al-quran-editions/app-update.json" \
  --file /tmp/app-update.json --content-type application/json \
  --cache-control "public, max-age=300" --remote   # --remote is required, easy to forget
```
Verified: `curl https://alquranreader.com/app-update.json` → 200, correct JSON.

**Still open — needs the owner, not an agent:** `CLOUDFLARE_API_TOKEN` is not
set as a GitHub secret. `CLOUDFLARE_ACCOUNT_ID` and `APP_UPDATE_R2_BUCKET`
*are* now set (values: account id `6272118b8114f9cbf1beb27b2a572dcc`, bucket
`al-quran-editions`). Deliberately did not mint an API token — that's a
credential-creation action the owner should do themselves via
dash.cloudflare.com → My Profile → API Tokens, scoped to "Workers R2 Storage:
Edit" for this account, then:
```bash

```
Until that's set, `flutter-release.yml` prints a `::warning::` on each
release (won't fail the build) reminding that the config wasn't published.
**Next release after the token is set should be watched once** to confirm the
new verification step passes end-to-end.

Full detail: see the "Soft-update config publishing" section of
[release.md](release.md), which was updated with the Worker's rationale.

## 3. Salat notifications not firing when app fully closed — FIXED, needs on-device confirmation

**Symptom:** Salat notifications didn't fire on lock screen when the app was
fully closed (killed, not backgrounded) — Sunnah Reminders and other apps'
notifications (Sadiq, Nusuk) worked fine in the same conditions.

**Root cause:** `PrayerNotificationsCubit.enable()`
(`lib/features/prayer_times/presentation/cubit/prayer_notifications_cubit.dart`)
only requested the basic `POST_NOTIFICATIONS` permission. Unlike
`RemindersCubit` (Sunnah reminders), it never requested exact-alarm
permission or battery-optimization exemption. Without those, Android silently
downgrades scheduled notifications to `inexactAllowWhileIdle`, which
aggressive OEM skins (and stock Doze) defer or drop once the app process is
killed — exactly the class of problem `RemindersCubit` already solves for
Sunnah reminders (see the `reminders-oneplus-test-device` memory note re:
OnePlus/OxygenOS needing Auto-launch + Unrestricted + lock-in-Recents).

**Fix:** brought `PrayerNotificationsCubit` to parity with `RemindersCubit`:
- `enable()` now calls `requestExactAlarmPermission()` and
  `requestBatteryOptimizationExemption()` (guarded on
  `isBatteryOptimizationExempt()`), same sequence as reminders.
- Added `fixReliability()` / `fixExactAlarms()` methods.
- Added `batteryOptimized` / `exactAlarmsAllowed` fields to
  `PrayerNotificationsState`, populated in `_reschedule()`.
- Wired the existing `_ReliabilityHint` banner (same widget Sunnah Reminders
  already uses) into `_SalatNotificationsSection` in
  `lib/features/navigation/presentation/pages/reminders_settings_page.dart`,
  so users now get the same "tap to allow background activity" self-heal
  prompt Sunnah Reminders has.
- 5 new unit tests in `test/features/prayer_times/prayer_notifications_cubit_test.dart`
  mirroring the equivalent reminders tests.

**Not yet done:** on-device verification. This is a real-device/OEM-timing
bug by nature — `flutter analyze` and the full test suite
(613 tests) pass, but per project convention (`testing-required-for-changes`
+ the general "test UI changes in a real browser/device" rule) this needs to
actually be exercised on the OnePlus 15R test device: enable Salat
Notifications, confirm the new reliability banner appears/disappears
correctly, grant the permissions, lock the phone, kill the app from Recents,
and confirm a notification still fires at the next prayer time.
